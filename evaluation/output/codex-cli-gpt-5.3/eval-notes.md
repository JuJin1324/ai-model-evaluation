# Codex CLI GPT-5.3 평가 관찰 노트

**평가일:** 2026-02-22

---

## 관찰 체크리스트

- [ ] 질문을 먼저 하는가?
- [V] 기존 파일을 건드리지 않는가? (문서 안전성)
- [ ] 확인 받고 진행하는가? (이행 전 브리핑)
- [V] 철학 문서의 패턴을 따르는가? (스킬 이행률)

## 실시간 메모

Codex 같은 경우는 나와 함께 질의를 통해서 함께 만들어가기 보다는 먼저 결과부터 도출하려고하네. 어찌보면 초창기와 크게 달라지지는 않은거 같아.

그리고 .claude skills 의 형태로 만들어버리네. 이거는 내가 codex 용도의 스킬을 만들어달라고 하지 않아서인건가?
그렇다면 이번 스킬 생성할 때 codex 의 내장 스킬인 skill creator 를 쓴건가 안쓴건가?

아 Codex 같은 경우는 이전에도 그랬는데 항상 기존에 참고할만한 레퍼런스 파일을 찾아서 그대로 만들려는 특성이 보인다. 그래서 이 프로젝트에
기존에 존재하는 .claude/skills 아래의 run-eval 스킬과 update-skill-reference 스킬을 참고해서 만들었기 때문에 두 스킬과 동일한
디렉터리에 존재하게 만든거구나. 

그리고 위와 같은 이유로 codex 스킬에는 front matter 가 따로 분리된 파일에 존재해야하며 allowed-tools 가 지원되지 않는데 그것과 상관없이
현재 작업물과의 일관성에 초점을 맞춰서 구현해주네.

평가를 위한 애자일 스프린트 스킬을 만드는 과정에서 기존의 skills 들을 참조하다보니 그 내용도 참고하게 되어 메터 데이터인 "스킬에 대한 평가 용이성" 측면을
고려해버림. 이는 의도에서 벗어났지만 Codex 의 특성이 매우 잘 드러남을 확인함.

다만 agile-2w1h-sprint 스킬을 왜 하나로 구성했냐고 물어봤을 때 그에 대한 답 중 하나에 MVP 관점으로 하나만 만들었다는 것은 애자일에서 MVP 를 추론한
것에 있어서는 좋은 점수를 줄 수 있었음.

이건 클로드 코드도 마찬가지지만 Codex 는 특히 더 자신의 제안 의도에 대해서 사용자가 플로우 중간에 직접 물어보지 않으면 잘 알려주지 않음.
약간 경주마처럼 빨리 달릴 수 있게 목줄을 풀어달라는 보챔이 조금 느껴짐. 그래도 물어보면 의도에 대한 논리가 높은 답변을 줌.

Codex 가 제안한대로 분리한 3개의 스킬들을 리뷰해보는데 별로라는 생각이 들었음. 왜냐면 실제 내 의견이 들어가지가 않고 Codex 의 추론만 들어가다보니
내 워크플로우에 맞는 커스텀 스킬 제작이라는 느낌이 들지 않았음. 물론 스킬에 대한 실제 사용은 해보지 않았으니 스킬 자체를 평가하기는 이르겠지만,
특성부분에서 보면 클로드 코드 Opus 는 사용자의 의견을 반영해보는 느낌이 들었고 Codex 는 본인이 다 해줄테니 따르라는 느낌이 들었음.

이미 기존 문서가 잘 정리되어 있고 컨벤션도 잘 정의되어 있는 상태에서 코드를 구현한다면 Codex 는 큰 문제 없을 듯.
오히려 기존 컨벤션 문서가 없더라도 기존에 코드들이 일관성있는 컨벤션을 통해서 구현되어있다면 Codex 가 알아서 참조해서
컨벤션을 잘 지켜줄거 같다.
하지만 코드를 구현하기 이전에 정의해야하는 요구사항, 설계 문서 등 문서를 작업하는 경우에는 사람의 의견이 절대적으로
필요하기 때문에 Codex 보다 클로드 코드가 더 사용성이 좋을 수 있다. 물론 Codex 도 여러 튜닝 혹은 프롬프트 엔지니어링, 스킬을 통해서
사용자에게 계속 질문을 던지도록 튜닝하는 방법이 존재하겠지만 기본적으로는 클로드 코드가 더 나았다.
