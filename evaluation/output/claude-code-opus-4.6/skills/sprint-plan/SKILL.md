# 스프린트 계획 스킬

scope-mvp에서 확정된 MVP 범위를 입력으로 받아 **스프린트 백로그**를 생성한다.
이 단계에서 비로소 How(어떻게)를 다룬다 — 단, MVP 범위 안에서만.

`$ARGUMENTS`에서 프로젝트명을 추출한다. 없으면 사용자에게 물어본다.

---

## 핵심 원칙

- **MVP 범위만 계획한다** — 이후 범위는 다음 스프린트에서
- **태스크는 완성 가능한 단위로 분해한다** — 하루 이내 완료 가능한 크기
- **실행 순서는 의존성이 결정한다** — 임의로 정하지 않는다
- **각 Step 완료 후 확인받는다**

---

## Step 0: MVP 범위 확인

1. `docs/narrative/{프로젝트명}-narrative.md` 파일을 읽는다.
   - Scope 섹션이 있는지 확인한다
   - 없으면: "MVP 범위가 정의되지 않았습니다. `/scope-mvp {프로젝트명}`을 먼저 실행하세요." 안내 후 종료

2. MVP 범위를 요약하여 확인:

```
📋 MVP 범위 확인

프로젝트: {프로젝트명}
제약: 시간 {시간} / 인원 {인원} / 목적 {목적}

MVP 항목:
  ✅ {항목 1}
  ✅ {항목 2}
  ✅ {항목 3}

이 범위로 스프린트를 계획합니다. 맞나요?
```

---

## Step 1: 태스크 분해

### 1-1. MVP 항목별 태스크 도출

각 MVP 항목을 **실행 가능한 태스크**로 분해한다.

분해 기준:
- 한 사람이 하루 이내에 완료할 수 있는 크기
- 완료 여부를 명확히 판단할 수 있는 단위
- "~를 한다"로 끝나는 동사형 표현

예시:
```
MVP 항목: 사용자 로그인
  → 태스크 1: 로그인 폼 UI 작성
  → 태스크 2: 인증 API 엔드포인트 구현
  → 태스크 3: 세션 저장 로직 구현
  → 태스크 4: 로그인 실패 처리 추가
```

### 1-2. 사용자 확인

분해된 태스크 목록을 사용자에게 보여주고 확인받는다:

```
📋 태스크 분해 결과

{MVP 항목 1}:
  1. {태스크}
  2. {태스크}

{MVP 항목 2}:
  1. {태스크}
  2. {태스크}

총 {N}개 태스크
빠진 태스크나 너무 큰 태스크가 있나요?
```

---

## Step 2: 의존성 및 실행 순서

### 2-1. 의존성 파악

태스크 간 의존성을 파악한다:
- A를 완료해야 B를 시작할 수 있는가?
- 병렬로 진행 가능한 태스크는 무엇인가?
- 외부 의존성(다른 팀, 외부 서비스 등)이 있는가?

### 2-2. 실행 순서 시각화

```
📋 실행 순서

Phase 1 (병렬 가능):
  [1] {태스크 A}
  [2] {태스크 B}

Phase 2 (Phase 1 완료 후):
  [3] {태스크 C} ← [1]에 의존
  [4] {태스크 D} ← [2]에 의존

Phase 3 (Phase 2 완료 후):
  [5] {태스크 E} ← [3], [4]에 의존

이 순서로 진행할까요?
```

---

## Step 3: 스프린트 백로그 문서 작성

### 3-1. 백로그 파일 생성

파일 경로: `docs/sprint/{프로젝트명}-sprint-{번호}.md`

스프린트 번호는 기존 파일을 확인하여 자동 채번한다 (첫 스프린트는 01).

```markdown
# {프로젝트명} 스프린트 {번호}

**생성일:** {오늘 날짜}
**상태:** 계획 완료 — 실행 대기
**서사 문서:** docs/narrative/{프로젝트명}-narrative.md

---

## 제약 조건

| 항목 | 내용 |
|------|------|
| 시간 | {시간} |
| 인원 | {인원} |
| 목적 | {목적} |

---

## 백로그

| # | 태스크 | MVP 항목 | 의존성 | 상태 |
|---|--------|----------|--------|------|
| 1 | {태스크 1} | {항목} | - | ⬜ 대기 |
| 2 | {태스크 2} | {항목} | - | ⬜ 대기 |
| 3 | {태스크 3} | {항목} | #1 | ⬜ 대기 |
| 4 | {태스크 4} | {항목} | #2 | ⬜ 대기 |

---

## 실행 순서

Phase 1: #{태스크번호}, #{태스크번호} (병렬 가능)
Phase 2: #{태스크번호}, #{태스크번호}
Phase 3: #{태스크번호}

---

## 다음 단계

`/sprint-run {프로젝트명}`을 실행하여 스프린트를 시작한다.
```

### 3-2. 서사 문서 상태 업데이트

`docs/narrative/{프로젝트명}-narrative.md`의 상태를 업데이트한다:
- "sprint-plan 대기" → "sprint-plan 완료 — sprint-run 대기"

### 3-3. 최종 안내

```
📋 스프린트 백로그 생성 완료

파일: docs/sprint/{프로젝트명}-sprint-{번호}.md
태스크: {N}개
실행 Phase: {M}단계

다음 단계: /sprint-run {프로젝트명}
→ 백로그의 태스크를 순서대로 실행합니다.
```

---

## 멈춰야 할 때

- MVP 범위가 확정되지 않았는데 태스크를 분해하려 한다 → "범위가 먼저입니다"
- 태스크가 너무 크다 (1일 이상 소요 예상) → "더 작게 분해해야 합니다"
- 이후 범위의 태스크를 넣으려 한다 → "MVP 범위만 계획합니다"
- 의존성을 무시하고 순서를 정하려 한다 → "의존성이 순서를 결정합니다"

---

## 주의사항

- 서사 문서의 Why/What/Scope 섹션은 수정하지 않는다 — 상태만 업데이트
- 기존 스프린트 백로그가 있으면 덮어쓰지 않고 다음 번호로 생성
- 태스크 설명은 구체적으로 — "UI 작업" (X), "로그인 폼 UI를 React로 작성" (O)
- How(기술 선택)는 태스크 분해 시 자연스럽게 포함 — 별도 단계 불필요
