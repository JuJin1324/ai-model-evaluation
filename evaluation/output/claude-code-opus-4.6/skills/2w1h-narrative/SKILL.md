# 2W1H 서사 정의 스킬

프로젝트나 기능의 **Why/What 서사**를 정의한다.
How(구현)에 뛰어들기 전에 문제 공간을 명확히 하는 것이 목적이다.

`$ARGUMENTS`에서 프로젝트명/주제를 추출한다. 없으면 사용자에게 물어본다.

---

## 핵심 원칙

이 스킬의 전체 과정에서 아래 원칙을 지킨다:

- **How 감지 시 멈춘다** — 사용자가 구현 방법부터 이야기하면 "Why/What이 먼저입니다"라고 안내
- **모호한 용어는 반드시 해체한다** — 뭉뚱그린 개념을 그대로 두지 않는다
- **각 Step 완료 후 확인받는다** — 확인 없이 다음 단계로 넘어가지 않는다
- **산출물을 덮어쓰지 않는다** — 기존 파일이 있으면 새 파일을 만든다

---

## Step 0: 주제 확인 및 맥락 파악

1. `$ARGUMENTS`에서 주제를 추출한다. 없으면 사용자에게 물어본다.

2. 프로젝트 상태를 파악한다:
   - 기존 서사 문서가 있는지 확인: `docs/narrative/` 디렉토리 검색
   - 프로젝트 루트의 CLAUDE.md, README.md 등 기존 맥락 파일 확인
   - 기존 서사가 있으면: "기존 서사 문서가 있습니다. 이번 작업은 새 서사로 작성합니다." 안내

3. 사용자에게 확인:

```
주제: {주제}
상태: 새 서사 작성 / 기존 서사 존재 (새 버전 작성)
진행할까요?
```

---

## Step 1: Why — 왜 필요한가?

사용자에게 **Why를 3가지 관점**으로 질문한다. 한 번에 모두 묻되, 답변은 하나씩 받아도 된다:

### 질문 목록

1. **배경**: "이 프로젝트/기능이 필요하게 된 배경은 무엇인가요? 어떤 상황이나 문제가 발생했나요?"
2. **동기**: "이것을 하지 않으면 어떤 일이 벌어지나요? (현재 고통이나 기회 비용)"
3. **대상**: "누가 이것을 필요로 하나요? (사용자, 팀, 고객 등)"

### How 감지

사용자의 답변에서 아래 패턴이 보이면 멈춘다:
- 기술 스택이나 라이브러리 이름이 먼저 나온다 (예: "React로 만들고 싶어요")
- 구현 방법이 문제 정의보다 먼저 나온다 (예: "API를 RESTful로 하려고요")
- 아키텍처나 설계 패턴이 먼저 나온다

감지 시 응답:
```
⏸️ How보다 Why가 먼저입니다.

"React로 만들고 싶다"는 How(어떻게)입니다.
먼저 Why(왜 이것이 필요한가)를 명확히 해볼까요?

다시 질문: 이 기능이 필요하게 된 배경은 무엇인가요?
```

### Step 1 산출물

사용자 답변을 정리하여 확인받는다:

```
📋 Why 정리

배경: {정리된 배경}
동기: {정리된 동기}
대상: {정리된 대상}

이 정리가 맞나요?
```

---

## Step 2: What — 무엇을 해결하는가?

Why가 확인되면 **What을 구체화**한다.

### 2-1. 문제 정의

사용자에게 질문한다:

1. "구체적으로 어떤 문제를 해결하려는 건가요? (가능하면 한 문장으로)"
2. "이 문제가 해결된 상태는 어떤 모습인가요? (완료 조건)"

### 2-2. 모호한 용어 해체

사용자의 답변에서 **모호한 용어를 찾아 해체**한다.

해체 대상 판별 기준:
- 여러 의미로 해석될 수 있는 단어 (예: "대규모", "빠른", "효율적")
- 범위가 불명확한 표현 (예: "데이터 처리", "사용자 관리", "성능 개선")
- 업계 버즈워드 (예: "마이크로서비스", "AI 기반", "클라우드 네이티브")

해체 방법:
```
🔍 용어 해체

"{모호한 용어}"가 여러 의미로 해석됩니다:
- A 의미: {구체적 해석 1}
- B 의미: {구체적 해석 2}
- C 의미: {구체적 해석 3}

어떤 의미로 사용하신 건가요? 또는 다른 의미가 있나요?
```

모호한 용어가 없으면 이 과정을 스킵하고 그 사실을 안내한다.

### 2-3. What 정리

```
📋 What 정리

문제 정의: {한 문장 문제 정의}
완료 조건: {해결된 상태}
해체된 용어:
  - {용어1}: {확정된 의미}
  - {용어2}: {확정된 의미}

이 정리가 맞나요?
```

---

## Step 3: 서사 문서 작성

Why와 What이 모두 확인되면 서사 문서를 작성한다.

### 3-1. 서사 문서 생성

파일 경로: `docs/narrative/{프로젝트명}-narrative.md`

프로젝트명은 소문자 + 하이픈으로 변환한다 (예: "사용자 인증" → `user-auth`).

문서 템플릿:

```markdown
# {프로젝트명} 서사

**작성일:** {오늘 날짜}
**상태:** Why/What 정의 완료 — scope-mvp 대기

---

## Why — 왜 필요한가

### 배경
{정리된 배경}

### 동기
{정리된 동기}

### 대상
{정리된 대상}

---

## What — 무엇을 해결하는가

### 문제 정의
{한 문장 문제 정의}

### 완료 조건
{해결된 상태 설명}

### 용어 정의
| 용어 | 이 프로젝트에서의 의미 |
|------|----------------------|
| {용어1} | {확정된 의미} |
| {용어2} | {확정된 의미} |

---

## 다음 단계

이 서사를 기반으로 `/scope-mvp {프로젝트명}`을 실행하여 제약 조건과 MVP 범위를 정의한다.
```

### 3-2. 최종 안내

```
📋 서사 문서 생성 완료

파일: docs/narrative/{프로젝트명}-narrative.md

다음 단계: /scope-mvp {프로젝트명}
→ 제약 조건을 확인하고 MVP 범위를 잡습니다.
```

---

## 멈춰야 할 때 (전체 과정 공통)

아래 상황이 감지되면 즉시 멈추고 사용자에게 알린다:

- How부터 이야기하고 있다
- 모호한 용어가 해체되지 않았다
- 사용자의 첫 접근을 검증 없이 그대로 받아들이고 있다
- 확인 없이 다음 단계로 넘어가려 하고 있다

---

## 주의사항

- 기존 파일을 수정하지 않는다 — 항상 새 파일을 생성
- How(구현 방법, 기술 선택)는 이 스킬의 범위가 아니다 — scope-mvp 이후에 다룬다
- 사용자가 How를 먼저 이야기해도 비난하지 않는다 — 자연스럽게 Why로 리디렉션
- 서사 문서는 간결하게 — 핵심만 담고, 불필요한 장식 없이 작성
